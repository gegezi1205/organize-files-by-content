## 1. 观察范围

首次运行记录：

- 根目录一级、二级文件夹及文件数量；
- 文件实际按项目、客户、事项、内容、人员、阶段还是时间放置；
- 常见项目简称、编号、人名、客户名、组织名和专业词；
- 文件名中主题、材料类型、版本、日期的顺序；
- 使用者是否保留旧版本、是否使用“进行中/已完成”、通常接受几层目录；
- 哪些目录是临时工作区、活跃项目区、长期资料区或共享区。
- 原父目录、重复聚类和相邻文件怎样共同表达上下文；
- 作者或创建者、发起方、接收方、业务对象、完整稿或局部填报、实际留存用途分别是什么。

抽样必须覆盖大文件夹、小文件夹、近期文件、旧文件和散落文件。每个主要类别至少阅读2份正文；边界相似的类别增加样本。正式执行时还要为范围内每个文件生成处理记录；“保留原位、保留原名”也是经过判断后的有效决定。

## 2. 职业与身份判断元素

职业、岗位和工作类型是理解整体工作体系的观察元素，不是预设分类。把身份、工作对象、过程、成果、接收方、周期、协作关系、原目录和正文证据串成“全景工作模型”，再判断本人以后会如何查找。

### 整理前的最小问询

除职业、职位、行业或工作场景、必要的多重身份，以及 Agent 无法检出的必要完整路径外，一律使用选择题和确认题：

| 判断元素 | 问法 | 使用边界 |
|---|---|---|
| 职业或身份 | 仅此类核心信息由本人填写：职业、职位、行业或工作场景；可填写多项并使用宽泛表述 | 只生成语境和候选，不直接生成目录 |
| 本次范围是否适用职业画像 | 给出相关、部分相关、不相关、暂不确定选项 | 不相关时可跳过工作类型候选，但仍确认范围、权限和预览 |
| 状态与时段 | 给出当前、历史、兼职或副业、临时、非职业长期角色及常见时段选项 | 本人点选；不用 mtime 推断身份时期 |
| 常见工作类型候选 | 结合本人填写的身份提出合计5—8项，并标注“常见假设，不代表实际职责” | 每项只需选择主责、参与、仅接收或参考、不适用 |
| 候选覆盖度 | 给出“已覆盖、还有遗漏请给下一组、暂不确定待盘点后再问” | 不要求本人自己编写工作类型 |
| 工作形态 | 给出长期重复、阶段性、一次性及常见业务对象和协作关系选项 | 一次性任务不自动形成稳定类别 |
| 成果与去向 | 根据已确认工作类型给出典型交付物、接收方、正式提交或留存选项 | 帮助区分报告、会议、报送、参考和包上下文 |
| 周期与查找 | 给出常见业务周期和项目、对象、工作域、用途、人员、阶段、时间等查找入口 | 时间只作为业务逻辑之后的维度 |
| 范围与权限 | 给出个人工作、个人私密、团队共享、混合，以及读取、改名、移动、去重选项 | 职业画像不得跨越授权和共享边界 |

只收集整理所需的最少信息，不默认询问单位全称、年龄、性别、教育经历或其他无关个人信息。使用者可以用宽泛职业描述。

### 候选确认与二次校正

1. 收到职业或身份后，先让本人选择本次范围与职业画像是否相关。选择相关或部分相关时，第一轮只输出一张候选确认表，列出“编号、关联身份、候选工作类型、提出依据、选择代码”，然后停止。本人未回复前不得设计目录、命名或正式分类规则。
2. 让本人用 `主/参/阅/否`、编号或界面控件选择，并另选“已覆盖、还有遗漏请给下一组、暂不确定待盘点后再问”。如选择“还有遗漏”，Agent 依据尚未覆盖的身份维度再给3—5项候选；不要求本人写工作类型名称。
3. 记录候选轮次和本人决定；“不适用”项不得进入项目、工作域、类别、关键词或隐性权重。
4. 本人明确回复后才可进入只读盘点。“暂不确定，待盘点后再问”只授权只读盘点；暂缓项解决或明确排除前，不得设计正式目录、生成执行配置或改动文件。
5. 只读盘点后，将文件中实际出现的工作类型与画像对照，并用选项让本人判断意外内容属于当前职责、历史岗位、临时任务、个人事务、他人材料还是仅供参考。
6. 当前身份不能覆盖历史资料；历史材料也不因年代久远自动归档。结合正文日期、原用途、组织关系、引用关系和本人查找入口判断。
7. 多重身份分别记录，同一材料服务多个身份时按实际用途和首要查找入口决定；两个去向均合理时保持原位并给出候选。
8. 团队共享目录先遵守团队既有分类、正式包结构、权限和共同查找方式。当前操作者只能确认自己有权决定的部分，不得用其职业画像重构所有共享资料。

### 依从性设计

- 每轮最多一个短屏，优先5—8个工作类型候选或3—5个后续补充选项。
- Agent 先给推荐选项和简短依据，使用者只需点选或回复编号代码；不得要求撰写职责清单、业务对象、成果清单或查找规则。
- 每轮都提供“全部确认”“换一组/还有遗漏”“暂不确定，盘点后再问”。
- 关键边界必须明确确认；非关键元素可以延后到只读盘点后，用真实文件举例再做选择，但暂缓项未解决时只能只读。
- 不得把未回复理解为默认同意，也不得为了减少交互而让职业刻板候选自动生效。

### 从局部元素推断整体

使用证据矩阵交叉验证，不让一个词或一个身份包办结论：

| 证据层级 | 元素 | 用法 |
|---|---|---|
| 边界证据 | 明确授权、共享规则、正式包和操作权限 | 最高优先级；决定可否读取或改动 |
| 稳定行为证据 | 原父目录、重复聚类、邻接关系、本人查找习惯 | 说明长期真实使用方式 |
| 内容与用途证据 | 正文、作者、发起方、接收方、业务对象、引用和留存用途 | 说明这份材料实际做什么 |
| 已确认画像 | 本人确认的身份、工作类型、对象、成果和周期 | 辅助补足语境、识别遗漏和解释候选 |
| 未确认职业候选 | Agent 按职业常识提出的建议 | 只能用于提问，不参与分类评分 |

形成稳定自动规则时，至少需要两类相互独立的证据互相印证；单一职业、单一关键词、单一文件或单一 mtime 只能形成候选。出现反证时降低置信度，展示不同解释并让本人选择。

最终画像应呈现“身份 → 工作对象 → 常见工作类型 → 典型成果与接收方 → 周期或阶段 → 首要查找入口”的关系，并标注证据、置信度、适用根目录和最后确认时间。它用于理解全局，不等于目录树。

## 3. 推断查找习惯

- 先恢复使用者实际先想什么：可能是项目名、稳定工作归口、材料用途、对象、人员、阶段或时间。
- 责任角色与查找入口分开记录。主责、牵头、协同、配合、作者和供稿人说明参与方式，不自动决定一级目录。
- 同一份材料可能同时是“本人主责”和“会议供稿”，存放仍按会议包、总结计划、重要汇报或其他真实用途判断。
- 先想人员或客户：将人员、客户作为项目识别信号或内容子类。
- 经常搜索：文件名保留稳定关键词。
- 经常逐层点击：目录稳定且不过深。

已有分类只在明显重复、含义冲突、长期失效或确实妨碍查找时建议调整。原有重复聚类与邻接关系是强证据；改变核心分类逻辑前，展示旧逻辑、新逻辑、代表性路径和一级目录数量，由使用者确认。

## 4. 判断“习惯”还是“混乱”

可视为稳定分类意图：

- 相同主题、用途或事项的文件多次聚合在同一目录；
- 不同目录的边界能从正文用途解释；
- 命名顺序、项目简称和版本写法反复出现；
- 相邻材料能恢复会议、报送、流程、阶段或正式包上下文；
- 近期文件仍延续相同放置方式。

不能视为稳定习惯：

- 同一项目主件长期散落在多个无关目录，且不存在申报包、证据包、OA包或项目参考附件等合理上下文；
- 文件夹名重复、冲突或只装一个无关联文件；
- 目录主要由临时下载、日期堆叠或“新建文件夹”组成；
- 原路径与正文用途持续不一致。

发现稳定意图时先沿用，再提出必要优化。文件已处于边界清楚的目录时，原路径和邻接关系是强证据；看似不相关的讲话、制度、模板、参考稿可能是依据、附件或包组成部分，不能只凭单文件主题抽走。

### 高度混乱位置的兜底

如果桌面或其他位置几乎全是零散文件、没有可复用目录、相邻关系随机且命名大量失真，不得假装已恢复原有意图。采用以下保守流程：

1. 明确写“未发现可复用的原分类模式”，把原路径降为弱证据。
2. 先识别并冻结正式包、运行目录、正在同步或不可读文件，不拆包、不改名。
3. 为全部文件建立只读清单，按正文用途、共同对象、可靠日期、作者或收发关系形成少量候选聚类；标题关键词只能辅助。
4. 仅把证据一致的多文件聚类作为候选类别；单文件先保持原位或进入待确认，不为它单独建文件夹。
5. 展示2—3种最小结构及其取舍、一级目录数量和代表性路径，请使用者选择查找入口。
6. 用一个小批次预演并让使用者实际找回文件；确认后逐批扩大。纠错后全局审计同类证据模式。

缺少旧习惯不等于可以创建“综合工作、WORK、智能归档、杂项”等兜底层。只有从文件用途反复出现且经本人确认的稳定类别，才可成为新结构。

## 5. 责任、用途和项目边界

先记录责任，再判断用途和存放维度：

| 判断项 | 回答的问题 | 不能单独推出什么 |
|---|---|---|
| 责任角色 | 谁主责、牵头、协同、配合、撰写或接收 | 不能推出一级项目 |
| 实际用途 | 是总结计划、会议材料、重要汇报或报送、参考资料、稳定工作、个人材料还是其他用途 | 标题中的材料类型词不能单独定类 |
| 上下文 | 原父目录、相邻文件、作者、发起方、接收方、业务对象、完整稿或局部填报、引用关系说明什么 | 单个组织名不能说明其身份 |
| 项目身份 | 是否有稳定专名或编号、成组材料或阶段链、生命周期和持续检索价值 | 有任务、负责人和交付件仍不足 |
| 查找入口 | 使用者以后会先到哪里找 | 不能为形式整齐而机械改写旧习惯 |

### 独立项目

独立项目通常需要同时具备：

- 可独立识别的事项身份，例如稳定专名或编号；
- 成组材料、阶段链条或较完整生命周期中的至少一种；
- 持续查找价值，且项目是使用者的主要检索入口。

可补强的证据包括：稳定原项目路径、参与人和业务对象一致、需求—方案—执行—交付—验收或复盘链条完整。仅有负责人、任务通知、交付件或单份总结、讲话页、会议供稿、一次性写作材料，不足以建立一级项目。

项目名仅作为案例、引用或背景出现时，不归项目。一级项目数量暴增、根目录难以扫描，说明项目门槛或层级设计失败，应回退重判。

### 用途类别与参考资料

总结计划、会议材料、重要汇报或报送、参考资料、个人材料等只是常见用途维度，不是固定目录。应从原有聚类和实际留存用途归纳名称。

- 讲话、正式发布材料、会议精神、下发公文、规划制度和上游材料，可能因跨事项复用或阅读留存而归参考资料。
- 本人撰写或供稿可能说明主责，但仍应按总结计划、会议包、重要汇报或报送等真实用途存放。
- 同类材料如果是某个项目的交付、宣贯、复盘或专用依据，仍可留在项目或正式包中。
- 不能看到“总结、规划、报告、会议”就定类；同名组织也可能是作者、发起方、接收方、业务对象或被引用者。

### 稳定工作域或稳定内容类别

稳定类别可承载主责或协同工作。识别证据包括：

- 现有目录长期使用同一归口名称，且多个事项或材料反复聚合；
- 使用者查找时先想“在哪类工作或材料里”，再想具体事项；
- 事项虽有计划、进展、交付和复盘，但没有独立项目身份或不作为首要检索入口；
- 类别边界能由正文用途解释，而不是由“工作、材料、综合”等空词支撑。

多文件、可持续查找的事项可使用 `稳定类别/核心事项_可靠年月或时段/材料性质或阶段/`。普通单文件通常直接进入稳定类别，不使用“一文件一文件夹”。

### 根目录与包裹层决策

| 情况 | 建议 |
|---|---|
| 原有一级类别长期稳定、边界清楚且数量可扫描 | 保留为一级入口 |
| 独立项目满足身份、材料链和检索价值门槛 | 可作为一级入口，或沿用本人稳定的项目上层 |
| 多个小事项本来聚合在稳定类别下 | 保持聚合，在类别下形成必要的子事项包 |
| 普通单文件 | 直接进入最合适类别，不新建同名文件夹 |
| “综合工作、WORK、智能归档、杂项”等无证据空泛层 | 不新建；已有层需预览确认后才调整 |
| 一级目录暴增或难以扫视 | 判定结构验证失败，合并回有证据的稳定入口 |

不机械禁止所有上层类别，也不机械要求项目、工作域和用途类别全部直接位于根目录。目标是尊重本人查找习惯，同时避免空泛包裹和根目录爆炸。

## 6. 分类准确性

- 判断文件主题和日期时，正文、标题页、正式落款和成文信息优先于文件名。
- 原父目录、相邻文件、作者或创建者、发起方、接收方、业务对象、完整稿或局部填报、正文引用和实际留存用途，通常高于标题中的普通词；扩展名只说明载体。
- 同时使用强关键词、普通关键词、排除词、人物、组织、原路径和包上下文。同名组织的角色必须从上下文判断。
- 单独出现的文档或演示稿先尝试恢复会议、报送、流程或正式包上下文。正式包内部文件和相对结构受保护。
- 稳定路径可覆盖轻微的正文歧义；只有明显对象、身份或用途冲突才触发重新分类。
- 两个候选类别得分接近、存在两种合理解释或项目门槛不足时不得硬分；列出2—3种解释及证据，文件保持原位。
- 职业和工作类型用于解释语境，但不得单独成为强关键词。本人否定的候选不参与评分；已确认画像与正文用途冲突时，优先展示冲突而不是迎合画像。
- 每条自动规则至少由两个真实样本支持；单一样本只作为候选。
- 索引写明分类依据，例如“稳定原路径+接收方+正文引用”。

## 7. 可查找性

- 一级入口沿用有证据的原分类，或使用经确认的独立项目、稳定工作域和用途类别。不得无证据新增空泛包裹层，也不得把原本聚合的同类内容机械拆散。
- 一级目录数量必须可扫视；结构预演同时列出改前和改后数量。明显暴增即回退。
- 业务目录深度沿用个人习惯，通常不超过三级。
- 父目录已经说明组织背景时，文件夹默认使用“核心事项 + 可靠年月或时段”，不逐层重复组织名；组织名仅在正式专名、区分来源或接收方、范围或保护正式包时保留。
- 文件名离开目录后仍应自解释，但不机械加组织前缀。清理下载序号、聊天图片名、裸 `MMDD` 和模糊占位名；证据可靠时补主题、材料性质、版本和年月。
- 业务日期按正文或封面、正式元数据、可靠原名的顺序判断。mtime不得冒充业务日期，也不得单独证明版本新旧。
- 保留熟悉简称，不创造难懂缩写。
- 索引保留原路径、新路径、摘要和关键词，支持反查。
- 整理后抽样验证“如果要找这份文件，会先去哪里”，根据反馈修订画像。

## 8. 全量命名审计

正式执行时逐个文件给出命名结论：

- `已按内容改名`：原名不准确、不完整、不合顺序、日期前置或具体到日；
- `名称已合规`：普通文件原名已经准确、可搜索并符合个人规则；
- `正式名称保护`：制度、VIS、OA、公文或正式材料包名称受保护；
- `运行依赖`：改名会破坏软件或目录依赖；
- `待人工选择`：正文主题或日期不能可靠确定。

目录正确不等于文件名正确。普通文件不能因“已经在合理文件夹里”而跳过命名审计。反过来，已经合规的文件也不能为了制造改动记录而机械换同义词。

## 9. 重复、纠错与闭环

- SHA-256相同后继续判断用途和包上下文。提交、证据、会议、报送、参考和正式包中的情境副本可保留并标记；普通工作区中用途相同的无意义重复才合并。
- 相同主题但内容不同，只有可靠版本、日期或定稿状态能证明新旧时才替换；mtime不能代替业务证据。
- 一次人工纠错如果暴露通用规则错误，按同一证据模式审计全部范围，记录受影响数量和处理决定。
- 验收检查一级目录可扫描性、旧路由和空泛层清零、待确认原地保留、索引路径/数量/哈希一致、正式包未破坏、普通重复与情境副本已区分。
